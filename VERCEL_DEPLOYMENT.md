# Alatau Doors: публичная демонстрация на Vercel + Neon

Подготовлено 28 октября, обновлено 29 октября 2026. Репозиторий содержит работающий адаптер PostgreSQL, отдельные миграции, наполнение вымышленными данными, ограниченный публичный режим и тесты.

Текущее состояние: создан приватный репозиторий `AASSAA17/alatau-doors` и отдельный Neon Free проект `alatau-doors-demo` (`summer-lake-34805999`, Frankfurt, PostgreSQL 18, база `alatau_demo`). Миграции и вымышленное наполнение применены. Роль `alatau_demo_app` создана через SQL с ограниченными правами; секреты находятся только в исключённых из Git локальных файлах. Повторная миграция и проверка режима прошли. Три интеграционные проверки прошли как с локальным HTTPS-сервером и настоящей Neon, так и на опубликованном Vercel-сайте: регистрация/сессии/избранное, полный процесс ролей, ограничения публичного ADMIN.

**Опубликовано:** [русская версия](https://alatau-doors-demo.vercel.app/ru), [казахская версия](https://alatau-doors-demo.vercel.app/kk). [Проект Vercel](https://vercel.com/aassaa17/alatau-doors-demo) находится на Hobby. GitHub App установлен только для `AASSAA17/alatau-doors`. `BETTER_AUTH_URL` точно совпадает с `https://alatau-doors-demo.vercel.app`. Runtime-переменные добавлены как Sensitive только в Production; owner URL, seed-флаги и файлы доступов в Vercel не передавались. Preview окружение не настроено и не получает доступ к общей базе. Бесплатный Vercel Hobby используется только для некоммерческой неофициальной демонстрации; перед коммерческим использованием нужно отдельно проверить подходящий тариф.

Для приватного просмотра облачных доступов на исходном Windows-компьютере откройте `.local/OPEN-CLOUD-ACCESS.cmd` двойным щелчком. Он расшифровывает памятку только в локальном интерактивном терминале и показывает аккаунты. Новый BUYER может зарегистрироваться без кода приглашения. Эти значения не сохраняются в дополнительный открытый файл. Альтернатива для аккаунтов: `npm.cmd run cloud:accounts`. Не запускайте команды просмотра доступов в CI или в чат-инструментах. Для одновременного показа трёх ролей используйте разные профили браузера; обычные вкладки одного профиля разделяют cookie.

Следующие разделы — воспроизводимая инструкция и справочник обслуживания. Создание ресурсов и первоначальное наполнение уже выполнены; не создавайте их повторно при обычном обновлении сайта. Push в `main` запускает новое production-развёртывание. Изменение env требует нового deployment, а миграции выполняются отдельно и явно.

Это демонстрационный стенд, не коммерческая production-система. Каталог, цены, наличие, интерьеры и заявки вымышленные. Не вводите реальные персональные данные. Внешние сообщения, платежи и отправка в WhatsApp отсутствуют. Все участники используют общую демонстрационную базу; изменения ADMIN видны другим посетителям.

## 2. Технологические решения и проверенные источники

- npm + существующий `package-lock.json`, Node.js 24.x, Next.js 16.4.3, Better Auth 1.7.14; App Router и Node.js runtime. Изменён слой доступа к БД, визуальная композиция сохранена.
- `pg` **8.23.1**, MIT, и `@types/pg` **8.23.1**, MIT. Better Auth принимает `pg.Pool` напрямую; Neon поддерживает обычный node-postgres. Это позволяет использовать полноценные транзакции на одном соединении без замены авторизации. Источники: [Better Auth PostgreSQL](https://better-auth.com/docs/adapters/postgresql), [Neon + Node.js](https://neon.com/docs/guides/node), [node-postgres transactions](https://node-postgres.com/features/transactions).
- `@vercel/functions` **3.6.1**, Apache-2.0: `attachDatabasePool` для жизненного цикла пула при Fluid Compute. Это осознанное исключение latest: проверенная версия 3.10.4 привносила уязвимую транзитивную ветку Zod через OIDC/cli-config; закреплённая 3.6.1 имеет нужный API и дерево без обнаруженных npm audit уязвимостей. [Официальная рекомендация Vercel](https://vercel.com/kb/guide/connection-pooling-with-functions), [справочник API](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package).
- Устаревший `@vercel/postgres` и Shopify не используются. Отдельный Neon serverless SDK не нужен: здесь выбран стандартный TCP/TLS-драйвер `pg`.
- PostgreSQL 18 использован в локальной проверке, [PostgreSQL License](https://www.postgresql.org/about/licence/). Условия облачной услуги Neon/Vercel и лимиты тарифа проверяет владелец перед созданием ресурсов; лицензии пакетов не означают бесплатный хостинг.
- Runtime использует **pooled URL**, миграции — **direct URL**. В runtime только транзакционные advisory locks; сессионный lock мигратора используется через direct endpoint. [Ограничения Neon PgBouncer](https://neon.com/docs/connect/connection-pooling).

## 4. Создание отдельной базы Neon

1. Создайте новый проект/пустую базу **только для демонстрации**. Не клонируйте базу с реальными пользователями. Выберите PostgreSQL 18 и регион Frankfurt, если доступны; `vercel.json` использует `fra1`.
2. Сохраните **direct connection string владельца** из Connect с выключенным connection pooling. Она нужна только для локальных миграций/seed. Не добавляйте её в Vercel.
3. Выберите будущий стабильный HTTPS-домен стенда — домен проекта `*.vercel.app` либо свой домен. Он будет единственным `BETTER_AUTH_URL`. Никаких `*`, путей, завершающего `/` или динамического разрешения всех preview-доменов.
4. Подготовьте отдельный локальный файл:

```powershell
if (!(Test-Path .env.cloud.local)) { Copy-Item .env.cloud.example .env.cloud.local }
```

Заполните его в редакторе. Режим — `public-demo`, провайдер — `postgres`. Укажите direct URL в `DATABASE_URL_UNPOOLED`, точный HTTPS-origin в `BETTER_AUTH_URL`. Создайте **новый независимый случайный** `BETTER_AUTH_SECRET` (48 случайных байт в base64url) в менеджере паролей либо локально через `node:crypto`. Не копируйте секреты основной/презентационной версии. `DATABASE_URL` до создания runtime-роли можно оставить пустым: maintenance-wrapper использует direct URL. Путь зашифрованной памятки по умолчанию — `.local/cloud-credentials.json`.

5. Явно примените схему, затем отдельно создайте вымышленные данные:

```powershell
npm.cmd run cloud:migrate
npm.cmd run cloud:seed
```

Для seed нужен `DEMO_SEED_CONFIRM`, указанный в примере окружения. Команда не читает локальные SQLite-базы. Создаются 12 вымышленных товаров, 5 новых пользователей с независимо сгенерированными паролями и 5 примерных заявок. Сессии созданных аккаунтов удаляются. Доступы сохраняются только в зашифрованной локальной памятке, защищённой новым облачным Better Auth secret.

Миграция имеет SHA-256 checksum, журнал версии и advisory lock. Повторная миграция проверяет checksum; повторный seed сохраняет изменения. Seed откажется наполнять немаркированную непустую БД и не разрешён в режиме `production`. Частично выполненное наполнение той же демобазы можно повторить с той же конфигурацией/памяткой; группа заявок и завершение seed транзакционны. При потере памятки не сбрасывайте данные: восстановите файл либо отдельно организуйте смену доступов. Runtime никогда сам не выполняет миграции или seed.

Не редактируйте уже применённый SQL-файл ради обхода checksum. Для будущих изменений нужны новая версия миграции и соответствующее расширение мигратора. Перед миграцией существующего стенда создайте резервную копию/точку восстановления средствами Neon и проверьте выбранную базу. Автоматических DROP/TRUNCATE/reset команд нет.

## 5. Ограниченный пользователь базы для приложения

**Не используйте owner URL в Vercel.** Приложение в `public-demo` проверяет права и откажется работать с ролью, способной менять защитные метки, удалять расчёты или создавать таблицы/роли/базы.

Создайте runtime-роль через **SQL** в новой демобазе:

```sql
CREATE ROLE alatau_demo_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS;
```

Задайте пароль через `\password alatau_demo_app` в интерактивном psql либо Reset password для этой уже созданной роли в Neon. Сохраните пароль в менеджере паролей. Не вставляйте пароль в исходники или SQL-файлы репозитория.

Именно создание роли через SQL существенно: роли, созданные кнопкой Add role/CLI/API Neon, получают членство в `neon_superuser`. [Документация Neon о ролях](https://neon.com/docs/manage/roles).

Затем выполните содержимое `scripts/postgres-runtime-grants.sql` **от владельца в выбранной демобазе** через SQL Editor или psql. Скрипт разрешает только нужные операции, оставляет метки режима только для чтения, а расчёты/историю/аудит — без UPDATE и DELETE. Таймауты SQL заданы на уровне роли, без session-настроек в startup-пакете PgBouncer.

В Neon можно дополнительно проверить:

```sql
SELECT pg_has_role('alatau_demo_app', 'neon_superuser', 'member'); -- должно быть false
SELECT rolname, rolsuper, rolcreatedb, rolcreaterole, rolbypassrls
FROM pg_roles WHERE rolname='alatau_demo_app'; -- все четыре флага false
```

Получите **pooled connection string** этой ограниченной роли для той же базы и поместите её в `DATABASE_URL` в `.env.cloud.local`. Убедитесь, что выбран именно `alatau_demo_app`, а hostname содержит pooler. Сохраните SSL-параметры Neon; приложение принудительно проверяет TLS-сертификат удалённой БД. Не устанавливайте `NODE_TLS_REJECT_UNAUTHORIZED=0`.

Проверьте готовность выбранной базы без публикации:

```powershell
node --env-file=.env.cloud.local --import tsx scripts/check-database-mode.ts
```

Ожидается `Database mode accepted.` и код 0. Проверка читает метки и права, ничего не создаёт.

## 7. Настройка и публикация Vercel — после согласования

1. Import Git Repository → ваш приватный GitHub-репозиторий → Next.js → корень проекта.
2. Node.js **24.x**, install `npm ci`, build `npm run build`; output directory оставить стандартным Next.js. Включите Fluid Compute, если это отдельная настройка проекта. Регион `fra1` уже в конфигурации; согласуйте его с регионом Neon.
3. До Deploy внесите **только пять runtime-переменных** из таблицы в Production Environment. Режим приложения при этом остаётся `public-demo`, несмотря на название окружения Vercel Production и `NODE_ENV=production`.
4. Не подключайте Preview к этой же базе и не выдавайте production-секреты произвольным PR. Для отдельного preview нужны собственная пустая демобаза, секреты и фиксированный origin. Неоснащённый такими переменными preview должен завершаться ошибкой, а не использовать SQLite.
5. На время проверки оставьте Deployment Protection. После проверки владелец разрешает публичный доступ к витрине. Кабинеты требуют авторизации; доступы ADMIN/SELLER выдаются адресно выбранным участникам. Не размещайте пароли на сайте, в README, issue, публичном чате или query-параметрах ссылки.
6. Перед открытием ссылки настройте доступные на вашем тарифе Firewall/Bot Protection и уведомления/лимиты расходов. Это дополняет ограничения приложения, особенно для публичных GET-страниц. Автоматическое подключение платных опций не предусмотрено. [Deployment Protection](https://vercel.com/docs/deployment-protection).
7. Нажмите Deploy. Если итоговый домен отличается от запланированного, исправьте `BETTER_AUTH_URL` и локальную облачную конфигурацию и сделайте redeploy. Используйте для демонстрации только этот стабильный домен.

Настройка Better Auth: exact trusted Origin, Secure/HttpOnly/SameSite=Lax cookie, host-only cookie без общего родительского домена, срок сессии публичной демонстрации 12 часов, сессии хранятся в PostgreSQL, cookie cache выключен. Роль/активность повторно проверяются по БД; блокировка отзывает сессии. Auth HTTP endpoints ограничены allowlist; регистрация открыта без приглашения и создаёт только BUYER. [Better Auth rate limiting](https://better-auth.com/docs/concepts/rate-limit).

## 8. Доступы, ограничения и эксплуатация демонстрации

С 29 октября регистрация BUYER открыта без приглашения: имя, email и пароль от 12 символов. На телефоне используется та же форма `/ru/sign-up` или `/kk/sign-up`. Старый `DEMO_INVITE_CODE`, если остался в настройках ранее созданного окружения, больше не читается приложением и не нужен для нового deployment. Пароли существующих кабинетов и сессии не менялись.

Получить новые облачные доступы **только в своём терминале**:

```powershell
npm.cmd run cloud:accounts
```

Не используйте для облака `demo:accounts` или `presentation:accounts`: это другие пароли и другие базы. Сохраните облачные доступы в менеджере паролей до ротации Better Auth secret — его смена делает старую зашифрованную памятку нечитаемой и инвалидирует подписанные cookies.

Публичный ADMIN управляет вымышленным каталогом, настройками, назначениями, заявками и покупателями, но не создаёт сотрудников, не повышает роли, не отключает сотрудников и не меняет пароли общих seed-аккаунтов. Новые BUYER могут менять свои пароли. Управление сотрудниками в локальном demo сохранено полностью. Оператор облака управляет сотрудниками отдельно через доверенный административный процесс; публичного endpoint для этого нет.

Ограничения публичного режима хранятся в PostgreSQL и действуют на все экземпляры Vercel:

- 40 записей/минуту на пользователя, 300 записей/час суммарно; 180 приватных чтений/минуту на пользователя.
- 400 обращений к auth/минуту глобально; дополнительно Better Auth: вход 10/минуту по IP, обычные auth-запросы 200/минуту.
- 10 попыток регистрации с допустимыми данными за 24 часа суммарно; 50 пользователей максимум, включая seed. Вместимость дополнительно защищена транзакционным триггером БД.
- 200 заявок всего и 20 на покупателя; 60 товаров; 500 внутренних комментариев; 10 версий расчёта на заявку.
- Тела auth-запросов до 16 KiB, workspace до 100000 байт; серверная строгая схема данных и ограничения числа/размера строк.

Это небольшой общий стенд, не инфраструктура для массовой нагрузки. Не повышайте лимиты из-за автоматизированной атаки. При подозрении на злоупотребление закройте доступ средствами Vercel, отзовите сессии затронутых аккаунтов и заблокируйте их. После ротации секретов обновите окружение и выполните redeploy. Ограничение публичного доступа не удаляет уже созданные аккаунты.

Истёкшие session/verification/rateLimit записи можно удалять отдельным операторским обслуживанием с предварительной проверкой схемы и сроков хранения; автоматическое расписание во внешних сервисах не создано. Seed не очищает наполненный стенд. Для нового чистого показа используйте новую пустую демобазу, новые доступы/путь памятки и явные migrate/seed, сохранив прежнюю базу до согласованного удаления.

## 9. Проверки перед передачей публичной ссылки

Локальные команды проверки (Node 24; Windows — `npm.cmd`):

```powershell
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
npm.cmd run test:e2e
npm.cmd run test:postgres:setup
npm.cmd run test:postgres
npm.cmd run test:public-demo
npm.cmd audit
```

`test:postgres:setup` использует установленный PostgreSQL 18 из `C:/Program Files/PostgreSQL/18/bin`, создаёт **отдельный loopback-кластер на 55432** в `.local/postgres-test`. Сервис Windows на 5432 не используется. Другой путь задаётся `POSTGRES_TEST_BIN`. Альтернатива для CI — `PG_TEST_ADMIN_URL` к **одноразовому loopback** PostgreSQL; тестовые команды отказываются работать с удалённым адресом. Каждый прогон создаёт новую базу. Данные сохраняются локально для диагностики, пользовательские БД не сбрасываются. HTTPS-тест использует локальный сертификат и отдельную ограниченную SQL-роль.

После согласованного deploy вручную подтвердите на настоящем домене:

1. `/ru` и `/kk`, каталог/поиск/фильтры, мастер, выбор размера и подборка работают на телефоне и desktop.
2. В трёх отдельных браузерных профилях войдите BUYER → создайте заявку; ADMIN → назначьте SELLER; SELLER → уточните состав, сохраните расчёт; BUYER → проверьте сумму/историю. Внутренний комментарий покупателю не виден.
3. Новый BUYER регистрируется без приглашения по имени, email и паролю (от 12 символов). Попытка передать роль ADMIN/SELLER или чужой Origin отклоняется. Кабинеты не открываются без входа, чужие заявки недоступны. Избранное/подборка переживают повторный вход.
4. Cookie действительно Secure/HttpOnly/SameSite=Lax на конечном HTTPS-домене. После блокировки покупателя старые сессии больше не дают доступ.
5. Сделайте redeploy и проверьте сохранность заявки/расчёта/избранного. Просмотрите Vercel logs на ошибки подключения, TLS, роли и исчерпания пула; не публикуйте содержимое секретных переменных.

Локальные результаты и границы проверки фиксируются в `CLOUD_VERIFICATION.md`. Работа с PostgreSQL и HTTPS проверена локально; Neon pooler, сертификат фактического домена, Vercel edge и GitHub Actions требуют завершающей проверки в созданных владельцем облачных окружениях.

## 11. Google-вход для покупателей

Подготовлен в отдельной ветке от текущей демонстрации, без включения email/MFA.
Оба значения `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` — только серверные переменные.
Без них Google-кнопка скрыта, парольный вход работает. Частичная конфигурация останавливает приложение.
Не добавляйте NEXT_PUBLIC-префикс, секреты в Git или preview-окружения с production-базой.

Google Cloud: отдельный проект Alatau Doors Demo (`united-blend-513209-r8`), без billing.
OAuth Web application: origin `https://alatau-doors-demo.vercel.app`, единственный callback
`https://alatau-doors-demo.vercel.app/api/auth/callback/google`.
Только `openid email profile`, без offline access, Gmail/Drive и дополнительных разрешений.
Privacy URL: `https://alatau-doors-demo.vercel.app/ru/privacy` (есть казахская версия `/kk/privacy`).
Использование контактного Gmail организатор согласовал отдельно.
До принятия Google User Data Policy и создания OAuth-клиента требуется подтверждение владельца.
После этого сохранить secret в Sensitive Vercel Production env и выполнить redeploy.
Не публиковать Google-кнопку с тестовым client ID.

Google создаёт только BUYER с подтверждённым Google email. Совпадающий email не объединяет
парольный аккаунт автоматически. ADMIN/SELLER входят по ранее выданному паролю; Google callback
для них запрещён, как и для отключённых пользователей. Публичное повышение ролей запрещено.
Существующая email-регистрация остаётся без обязательной проверки email, согласно выбранной
владельцем версии demo. Это не является завершённой коммерческой системой безопасности.

PKCE и state-cookie проверяет Better Auth; сервер отдельно проверяет подпись, issuer, audience
и срок ID token официальной функцией Better Auth. Сырой ID token не сохраняется; access tokens
шифруются. Callback не принимает клиентские роли, scopes, ID tokens и внешние адреса возврата.
Новая Google-регистрация использует общий лимит 10/сутки и триггер 50 аккаунтов.

Проверка без подключения к Google и без настоящих данных:
`node scripts/test-public-demo.mjs --google --build`.
Тестовый симулятор провайдера существует только в `scripts/test-google-auth.ts`, отказывается
работать вне новой loopback-базы и не подключается к production. Браузерные проверки перехватывают
переход на Google до внешнего запроса. Реальный Google-вход проверяется отдельно после настройки
клиента и согласия владельца тестового Google-аккаунта. Такой тест не заменяется симуляцией.

На телефоне: открыть `/ru/sign-in` в Chrome/Safari, войти выданным облачным email/паролем —
ADMIN автоматически направляется на `/ru/admin`, SELLER на `/ru/seller`. Для смены роли сначала
выйти. Доступы показываются только локальным `.local/OPEN-CLOUD-ACCESS.cmd` в исходном проекте;
передавать их через менеджер паролей, не через Git, сайт или публичный чат.
