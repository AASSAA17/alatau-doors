# Защита аккаунтов — подготовленное подключение

Статус: объединено с Google-входом, email/SMS-адаптерами и гостевыми заявками. Включение строгого режима отделено от публикации кода.
Почтового сервиса и подтверждённого домена отправителя ещё нет. Существующие облачные
аккаунты, сессии, локальные SQLite и презентация на порту 3200 не изменяются этой подготовкой.

## Поведение

- В production, а также при AUTH_SECURITY=required требуется подтверждённый email (для BUYER с подтверждённым SMS допускается телефон). Для SELLER и ADMIN дополнительно
  требуется включённый TOTP и подтверждение второго фактора в текущем сеансе.
  Ограничение действует на сервере: workspace API, страницы кабинетов, избранное и подборку.
- Локальный APP_MODE=demo сохраняет прежний автономный режим. Для проверки строгого режима
  локально можно задать AUTH_SECURITY=required. Публичная демонстрация без этого флага сохраняет прежнюю политику. В production проверки обязательны независимо от флага.
- Письма подтверждения, восстановления и уведомления о смене пароля переведены на RU/KK.
  Ссылки действуют 15 минут. Подтверждение и восстановление одноразовые; сброс пароля отзывает
  все сеансы, но не отключает MFA. Подтверждение email само по себе не выполняет вход.
- Токен ссылки передаётся во фрагменте URL и удаляется из адресной строки после чтения.
  Пароли, ключ TOTP, резервные коды и ссылки не записываются в браузерное постоянное хранилище.
- Для первого подключения MFA организатор выдаёт одноразовый код, связанный с пользователем,
  действующий 15 минут. Его хеш хранится в БД. Код расходуется при попытке подключения;
  после ошибки пароля или закрытия страницы до сохранения ключа нужен новый код организатора.
- Пользователь вручную добавляет ключ в приложение-аутентификатор, сохраняет резервные коды
  и подтверждает шестизначный код. Секрет и резервные коды шифрует Better Auth.
  Постоянное доверие устройству и отключение MFA через публичный API запрещены.
- После пяти неверных попыток второй фактор блокируется на 15 минут. Дополнительно работают
  ограничения частоты запросов по IP; в публичной демонстрации — квоты писем по адресу и общая квота.
- Публичный сервер не может выпускать коды первоначальной настройки MFA: SQL-роль имеет только
  SELECT/DELETE на mfa_enrollments. Учётные записи с общими адресами @alatau.demo не получают
  письма восстановления; организатор должен перевести сотрудников на доступные им адреса.

## Почтовое подключение

Подготовлен Resend через официальный HTTPS API и встроенный fetch; новый пакет не требуется.
Провайдер ещё не подключён, доставка реальных писем не проверена.
Production или Vercel с AUTH_SECURITY=required откажет без настроенной почты. Публичная демонстрация без этого флага продолжает работать; функции доставки скрыты до подключения провайдера.

Переменные только на сервере, без NEXT_PUBLIC_:

| Имя | Назначение |
| --- | --- |
| AUTH_MAIL_PROVIDER | resend |
| AUTH_MAIL_FROM | Адрес отправителя на подтверждённом домене |
| RESEND_API_KEY | Ключ с правом отправки писем, хранить в секретах окружения |
| BETTER_AUTH_URL | Точный HTTPS origin приложения, без завершающего слеша |
| BETTER_AUTH_SECRET | Существующий секрет; его смена требует отдельного плана для зашифрованного MFA |

Проверить домен отправителя через DNS по инструкциям сервиса, настроить SPF/DKIM и политику DMARC,
отключить преобразование/отслеживание ссылок в письмах авторизации. Проверить доставку на реальные
контрольные адреса и мобильное открытие ссылки. Секреты не передавать в чат и не коммитить.
Ошибка отправки записывается без адреса и токена. В Vercel доставка выполняется через waitUntil.
Смена пароля остаётся успешной, даже если последующее уведомление не доставлено.

Тестовый транспорт AUTH_MAIL_PROVIDER=test допускается только вне Vercel, с loopback URL,
ALATAU_TEST_RUN и AUTH_TEST_MAIL_DIR внутри .local текущего проекта. Он записывает синтетические
письма локально; эти переменные нельзя переносить в облако. Тестовые файлы исключены из Git и deploy.

## Безопасное включение на опубликованном сайте

1. Подключить и проверить почтовый сервис. Подготовить отдельный preview с отдельной тестовой БД.
   Не включать AUTH_SECURITY=required на действующем сайте, пока пункты ниже не выполнены.
2. Сделать резервную копию/ветку Neon. Выполнить `npm run cloud:migrate` из приватного терминала
   с владельцем БД в DATABASE_URL_UNPOOLED, затем применить scripts/postgres-runtime-grants.sql.
   Миграция 003 добавляет таблицы защиты аккаунтов; 004 — хранилище изображений; Better Auth добавляет twoFactor и поля user/session.
   Старые строки не удаляются и не получают автоматическое подтверждение email или MFA.
3. Согласовать владельца каждого SELLER/ADMIN. Через закрытый операторский доступ заменить
   вымышленный email на доступный владельцу, сохранив user.id и связанные заявки; установить
   emailVerified=false и отозвать его сессии. Не отмечать адрес подтверждённым вручную.
   Не менять адреса реальных пользователей без их согласия. Общие кабинеты не использовать
   как неограниченные административные аккаунты для посетителей демонстрации.
4. На preview/в согласованное окно переключения владелец запрашивает письмо на /ru/verify-email,
   подтверждает адрес, при необходимости меняет общий пароль через /ru/forgot-password.
   До MFA кабинет остаётся закрыт. Неподтверждённые старые пользователи также проходят проверку email.
5. Организатор в своём интерактивном терминале выполняет
   `npm run cloud:mfa-enrollment -- <email-сотрудника>` и передаёт выданный код лично владельцу.
   Команда намеренно не выводит код в перенаправленный вывод/CI. Код не является кодом регистрации
   покупателя. Скрипт требует активного сотрудника с подтверждённым email, ещё без MFA.
6. Владелец входит, открывает /ru/security (или /kk/security), вводит код организатора и пароль,
   сохраняет ключ в Google Authenticator, Microsoft Authenticator или другом TOTP-приложении,
   сохраняет резервные коды отдельно от телефона, подтверждает текущий код.
7. Проверить вход BUYER, SELLER, ADMIN, запрет обхода MFA прямыми запросами, восстановление,
   доставку RU/KK и процесс BUYER → ADMIN → SELLER → BUYER. Только затем переключить публичный домен.

При потере телефона использовать одноразовый резервный код. При потере всех факторов нужен
отдельный ручной процесс проверки личности организатором; публичного сброса MFA по одному паролю нет.
Откат на старый код после включения требований вернёт менее строгую политику входа. Предпочитать
исправление вперёд или временное закрытие доступа; не удалять таблицы и не сбрасывать пользователей.

## Проверки

`npm run test:account-security` создаёт новую loopback PostgreSQL БД, ограниченную SQL-роль,
синтетические аккаунты и локальный почтовый ящик. Проверяются ссылки, истечение срока,
отзыв сеансов, MFA, резервные коды, блокировка, серверные права и ограничения частоты.
`npm run test:public-demo` проверяет действующую демонстрационную политику без обязательного MFA; строгий режим проверяется отдельно.
Оба runner принимают только loopback PostgreSQL. Не запускать их на Neon.

Для сохранения презентации проверять сборку в отдельной копии исходников со своей .next.
Не выполнять root build, seed или миграции против действующей презентационной БД во время показа.
