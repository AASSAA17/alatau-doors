# Alatau Doors — архитектура

## Подготовленное усиление авторизации

В рабочей ветке добавлены подтверждение email и восстановление пароля через Resend REST API,
а также Better Auth twoFactor (TOTP). В production или при AUTH_SECURITY=required для SELLER/ADMIN сервер требует user.twoFactorEnabled
и session.mfaVerified; старый сеанс с одним паролем не даёт доступ к рабочим данным.
Первую привязку защищает одноразовый операторский код в mfa_enrollments. Публичная SQL-роль
не может выпускать такие коды. auth_links хранит хеши одноразовых ссылок подтверждения.
Миграции добавляют схему, не перезаписывая данные. Локальный demo остаётся автономным.
Почтовый сервис пока не подключён; public-demo без AUTH_SECURITY=required сохраняет прежнюю политику.
Переход, ограничения и переменные описаны в [ACCOUNT_SECURITY.md](ACCOUNT_SECURITY.md).

## Изменение требований: три роли и постоянные данные

Это развитие существующего приложения. Запрет на авторизацию, минимальную админ-панель и БД отменён новым заданием. Продавец — сотрудник единственного магазина. Полноценная CRM, онлайн-оплата, рассылки, 1С, маркетплейс и сложный склад остаются вне объёма.

Целевая среда первой версии: один Node.js 24 сервер/VPS с постоянным локальным диском. SQLite (WAL, foreign keys, транзакции) через better-sqlite3. Не размещать этот адаптер на эфемерном диске Vercel/serverless или в нескольких независимых репликах; для этого нужен PostgreSQL-адаптер. Существующий ProductRepository сохраняется, источник становится серверным.

Better Auth управляет хэшированием паролей, подписанными HttpOnly cookie и серверными сессиями. Роли BUYER/SELLER/ADMIN и active читаются из БД при каждом защищённом запросе. Регистрация принудительно создаёт BUYER, поля role/active недоступны вводу. Смена роли и блокировка отзывают сессии. API проверяет Origin, JSON schema, сессию, роль и принадлежность записи. Не полагаться на скрытие UI.

Таблицы: Better Auth user/session/account/verification/rateLimit; products, variants, favorites, drafts, requests, request_items, quotes, request_events, internal_comments, store_settings, audit_log, schema_migrations. История публичного статуса отдельно от внутренних комментариев; DTO покупателя не содержит внутренних данных. Суммы вычисляет сервер, версии расчёта неизменяемы и содержат снимки названий, размеров, комплектации и цен. Архивирование не удаляет записи или историю.

Переходы: NEW → IN_PROGRESS → QUOTED → COMPLETED; отмена NEW/IN_PROGRESS/QUOTED → CANCELLED. Назначение администратора переводит NEW в IN_PROGRESS. Публикация расчёта переводит IN_PROGRESS в QUOTED. Изменение состава после расчёта возвращает в IN_PROGRESS и сохраняет предыдущую версию расчёта. Терминальные заявки неизменяемы. Продавец работает только с назначенными ему заявками. Пользователь не может подменить buyerId/sellerId/роль/итог.

Демо-инициализация отдельной командой: 12 товаров, администратор, два продавца и два покупателя. В БД пароли хэшированы Better Auth. Случайные исходные пароли находятся в зашифрованной локальной игнорируемой памятке .local/demo-credentials.json (AES-256-GCM, случайные nonce/salt, HKDF с отдельным контекстом из BETTER_AUTH_SECRET). Оператор получает доступы командой npm run demo:accounts; HTTP-метода для расшифровки нет. После переноса в менеджер паролей памятку можно удалить. Секрет находится в .env.local. Seed разрешён только для APP_MODE=demo и файла с суффиксом demo.sqlite; повторное выполнение не перезаписывает данные. Реальная база создаётся отдельно, seed для неё запрещён. APP_MODE=production требует явный non-demo DATABASE_PATH и HTTPS origin; БД с маркером seedComplete отклоняется даже после переименования файла.

Новые зависимости проверены по официальным источникам: better-auth 1.7.14 (MIT; Next 16/React 19), better-sqlite3 13.0.3 (MIT; Node >=22), zod 4.6.7 (MIT), tsx 4.23.15 (MIT), @types/better-sqlite3 9.6.0 (MIT). https://better-auth.com/docs/integrations/next, https://better-auth.com/docs/concepts/database, https://github.com/WiseLibs/better-sqlite3.

Маршруты кабинетов: /[locale]/account (покупатель), /seller, /admin; заявки /requests/[id]; общие профиль и избранное. Управление каталогом /admin/products, аккаунтами /admin/users, контактами /admin/settings. Вход /sign-in, регистрация /sign-up. Публичный каталог без авторизации.

Дата проверки зависимостей: 28 октября 2026. Проект начинался с пустой папки.

## Решения

- Next.js App Router, React Server Components для страниц, метаданных и загрузки каталога. Клиентские компоненты только для интерактивности.
- TypeScript strict. Tailwind CSS 4, CSS tokens и локальные компоненты shadcn/ui; Manrope для заголовков, Inter для интерфейса (локальные fontsource, без Google Fonts во время сборки).
- Палитра: #F7F6F2, #183F32, #202521, #D8C4A5. Интерьерная витрина с основным текстом 16–18px, читаемыми ценами/кнопками и умеренными скруглениями. Кабинеты используют те же цвета и шрифты, рабочие таблицы и формы. Motion учитывает prefers-reduced-motion.
- next-intl: URL /ru и /kk, словари messages/*.json; переключение языка сохраняет маршрут. Русский по умолчанию.
- Данные отделены интерфейсом ProductRepository, серверный SQLite adapter. Денежные значения — целые тенге, форматирование Intl.
- Zustand persist используется только для гостевого избранного и черновика. После входа избранное и черновики хранятся в БД.
- Поиск, сортировка и фильтры выполняются серверным repository над небольшим каталогом из SQLite; URL — источник состояния каталога. При росте каталога перенести фильтрацию непосредственно в SQL и добавить пагинацию.
- Все товары, характеристики, цены и AI-визуализации демонстрационные. Нет отзывов, утверждений о наличии, реальных адресов или телефонов. robots noindex.
- WhatsApp не подключён; никакие уведомления во внешние сервисы не отправляются. В этой итерации заявка создаётся внутри приложения.

## Структура

src/app/[locale] — маршруты и server layouts; src/components — общий UI; src/features — каталог, избранное, конфигурация; src/data — fixtures; src/lib — repository, форматирование и i18n; src/store — локальное состояние; src/types — domain contracts; messages — переводы; tests — Playwright.

## Завершение пользовательского пути

- `/door-finder` — отдельный публичный локализованный мастер. Ответы и шаг кодируются в URL, кнопка назад сохраняет текущие ответы. Серверный маршрут нормализует параметры и читает тот же repository/SQLite-каталог. Клиент фильтрует категорию и активные доступные варианты по цене одного полотна; размер вне бюджета нельзя добавить из результата. Количество не подменяет бюджет за полотно.
- `selection-client.ts` объединяет добавление из товара/мастера в существующий guest draft или BUYER draft. Отдельной корзины нет. При превышении лимитов — ошибка без обрезания. Вход с `returnTo=selection` допускает только этот фиксированный адрес; произвольный redirect не используется. Импорт гостевых позиций явный, объединяет с текущим черновиком и удаляет гостевую копию только после успешного сохранения сервером.
- `pricing.ts::priceLine` — вынесенная без изменения арифметика существующего серверного calculate. Сервер по-прежнему сам читает проверенные цены/варианты из БД. LineEditor и WhatsAppPreview используют общий previewSelection; при недоступной позиции показывают отсутствие расчёта, а не нулевую цену. Предпросмотр не является опубликованной версией и не записывается в quotes. В тексте только выбранные публичные позиции и цены, без профилей и комментариев.
- `src/data/editorial.ts` — типизированный RU/KK-источник для `/about` и `/projects`; никакой CMS. Каждая интерьерная идея использует отдельный имеющийся AI-ресурс и ссылку на работающую категорию. Реальных заказчиков, адресов, отзывов и сроков нет.
- Material (состав полотна), coating (покрытие) и finish (цвет/оттенок) отделены. Для точных старых demo-значений «Эмаль»/«Шпон дуба»/«Шпон ореха» read adapter показывает coating и неизвестный material. Новые seed-данные сразу нормализованы. Произвольные пользовательские значения и сохранённая БД не перезаписываются; historical quotes этих полей не содержат и не изменяются. ADMIN может заполнить отдельное необязательное coating RU/KK.
- Верхняя полоса кабинета — семантический ordered list этапов с отдельным пояснением отмены, без фильтров и без изменения серверного scope.
- Новые стили ограничены `completion.css`; принятая композиция старых экранов сохранена. Шапка ведёт в мастер, иконка/мобильная ссылка — в подборку; информационные маршруты доступны из футера.

## Принятая визуальная основа

- `visual-refinement.css` задаёт композицию витрины, боковые фильтры, трёхколоночный товар и адаптивные кабинеты. При ширине до 900 px те же строки таблиц отображаются карточками с локализованными `data-label`; данные, серверные действия и права едины для всех экранов.
- `WorkspaceNavigation` — клиентская граница для раскрытия меню/Escape/активного раздела. Список ссылок по роли по-прежнему формирует серверный `WorkspaceShell`. Footer выбирает компактный вариант для рабочих маршрутов.
- `CatalogControls` использует форму и связанные через `form` поля боковой панели, сохраняя URL как источник фильтрации. На телефоне панель раскрывается кнопкой. Нет фильтров по отсутствующим свойствам.
- Цены форматируются через Intl parts с единым разделителем групп; даты — числовые, в `Asia/Qyzylorda`. Это устраняет разницу fallback ICU между Node и браузером для KK; денежная арифметика и сохранённые версии расчёта не изменены.
- `src/data/presentation.ts` содержит профиль `visual-v1`. `scripts/presentation.mjs` задаёт отдельные DATABASE_PATH/BETTER_AUTH_SECRET/BETTER_AUTH_URL и путь зашифрованных доступов; профиль нельзя посеять в основную БД. Setup повторяемый, без удаления существующих записей; start/dev не запускают seed.
- `scripts/capture-presentation.ts` снимает только презентационную БД на порту 3200. Регрессия использует другие уникальные БД и порт 3100. Снимки разделены, storageState/секреты не экспортируются. Локальные служебные файлы исключены из Git и ESLint.
- Использованы прежние зависимости и четыре прежних AI-ресурса. Нет поддельной галереи, отзывов, адресов и гарантий из референса. Пустые контакты — один информационный блок; заполненные поля читаются из настроек администратора.

## Облачная демонстрация: PostgreSQL и Vercel

- Существующий проект и npm lockfile сохранены. Серверные изменения выполняются через `/api/workspace` и `/api/auth/[...all]`; Next Server Actions в проекте не используются. SSR читает тот же серверный слой, что и HTTP API.
- `src/lib/server/db.ts` предоставляет асинхронный интерфейс `prepare().get/all/run` и транзакции. `sqlite.ts` сохраняет native better-sqlite3, WAL, миграции и защиту production от локальных seeded-баз. `sql-dialect.ts` переводит только SQL приложения в PostgreSQL placeholders/quoted identifiers; пользовательские значения всегда передаются отдельно. Произвольный SQL от клиента не принимается.
- `DATABASE_PROVIDER` выбирает SQLite или PostgreSQL. Новый `APP_MODE=public-demo` допускает только PostgreSQL с маркером `cloud-v1` и ограниченной SQL-ролью. На Vercel SQLite и maintenance-флаги запрещены. Режим `production` продолжает отклонять наполненные demo-базы, включая PostgreSQL. Изменение NODE_ENV или имени SQLite-файла не отменяет проверку seed-маркера.
- `pg` 8.23.1 подключается к Neon через проверяемый TLS. Один process-global Pool, максимум 5 соединений, idle 5 секунд, connection timeout 10 секунд; `@vercel/functions` 3.6.1 подключает lifecycle пула. Ограничения времени SQL задаются SQL-роли. В облаке pooled runtime URL; direct owner URL используется только оператором. Источники и исключение latest для пакета Vercel описаны в `VERCEL_DEPLOYMENT.md`.
- AsyncLocalStorage удерживает один PoolClient от BEGIN до COMMIT/ROLLBACK. Транзакционный advisory lock сериализует доменные изменения небольшой общей демонстрации между экземплярами Vercel; revision проверяется после lock. Это сознательно ограничивает пропускную способность стенда. Сетевых сторонних вызовов внутри доменной транзакции нет. SQLite использует отдельную очередь транзакций; его синхронные запросы исполняются через тот же async-контракт.
- Каталог получает товары/варианты двумя запросами; расчёт загружает варианты пакетом. Денежные значения — целые тенге, PostgreSQL quote total BIGINT с безопасным диапазоном JS; parser откажется молча округлять небезопасный int64. История, цены в сохранённых quote snapshots, ID и публичные DTO сохранены.
- Better Auth использует исходный SQLite или официальный PostgreSQL adapter через pg.Pool. Проверка active перед созданием session выполняется через internalAdapter Better Auth, участвующий в его транзакции регистрации. Сессии PostgreSQL переживают перезапуск функции. Auth timestamps передаются как Date для PostgreSQL и epoch milliseconds для SQLite.
- `migrations/postgres/001_business.sql` и явный `cloud:migrate` создают отдельную схему после auth migrations. Checksum, версия и direct session advisory lock исключают незаметное изменение применённой миграции. Автоматических миграций во время сборки, обработки HTTP или запуска сервера нет.
- `cloud:seed` использует fixtures проекта, новые случайные пароли и новую зашифрованную памятку; не импортирует local users/account/session. Новая немаркированная база должна быть пустой. Повторный seed сохраняет данные. Статусы seed и группа заявок завершаются в одной транзакции. Для новых изменений схемы нужен следующий SQL-файл/версия и расширение мигратора, без правки checksum вручную.
- `public-demo.ts` задаёт права и распределённые лимиты. Публичный ADMIN не создаёт сотрудников/ADMIN и не повышает роли. Общие seed-пароли меняет оператор; персональные BUYER сохраняют смену пароля. Строгие DTO/Origin, scopes BUYER/SELLER, скрытые комментарии, отзыв сессий и snapshot quotes продолжают действовать. Регистрация BUYER открыта без приглашения: точный Origin, строгая схема name/email/password, 10 валидных попыток за 24 часа суммарно и 50 аккаунтов максимум, включая seed. Неверные данные отклоняются до расходования квоты регистрации. Вместимость дополнительно ограничена триггером БД.
- `postgres-runtime-grants.sql` оставляет runtime-роль без DDL, записи app_meta и изменения/удаления quotes/events/audit. Нужные изменения каталога, заявок, пользователей BUYER и настроек сохраняются. Это отдельный слой поверх проверок бизнес-ролей.
- Облачные настройки хранятся у оператора в `.env.cloud.local`, в Vercel только runtime secrets. Презентационный wrapper принудительно выбирает SQLite на 3200. Git/Vercel исключают `.local`, env-файлы с данными, DB и ключи. Инструкция, переменные и границы готовности — `VERCEL_DEPLOYMENT.md`, результаты — `CLOUD_VERIFICATION.md`.

## Подготовка к передаче: изображения и резервные копии

Миграция 003 добавляет auth_links/mfa_enrollments, Better Auth добавляет twoFactor и поля пользователя/сеанса. Миграция 004 добавляет media (bytea/BLOB). POST /api/media требует ADMIN, Origin и квоты; sharp 0.35.5 (Apache-2.0) декодирует только JPG/PNG/WebP до 20 МП, преобразует в WebP без метаданных. GET /api/media/[UUID] отдаёт публичный неизменяемый файл. Только существующие идентификаторы принимаются при сохранении товара. SQLite и PostgreSQL сохраняют прежние пути изображений. Ограничения 4 МБ вход / 1 МБ выход / 100 МБ общий объём заданы на сервере. Runtime SQL-роль имеет только SELECT/INSERT на media.

scripts/backup.mjs создаёт согласованные копии SQLite/WAL и PostgreSQL (pg_dump custom), шифрует AES-256-GCM отдельным ключом. Проверка расшифрования предшествует восстановлению; PostgreSQL restore разрешён только в новую автоматически созданную loopback БД. Инструмент предназначен для небольших баз до 256 МБ и требует приватного операторского окружения. Фоновое внешнее копирование не подключено. Детали и границы — BACKUP_RECOVERY.md, SALE_READINESS.md.
