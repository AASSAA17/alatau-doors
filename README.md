# Alatau Doors

Существующая витрина дополнена работающими кабинетами BUYER, SELLER и ADMIN, серверной авторизацией и постоянной базой данных. Неофициальная демонстрация: 12 вымышленных моделей, примерные цены и наличие, AI-изображения. Заявки сохраняются внутри системы; реальные письма, SMS, WhatsApp, платежи и доставка не выполняются.

Опубликован отдельный публичный режим **Vercel + Neon PostgreSQL** с ограниченным ADMIN, открытой регистрацией BUYER и независимыми доступами: [alatau-doors-demo.vercel.app](https://alatau-doors-demo.vercel.app/ru). Локальный SQLite и презентация на 3200 сохранены. Инструкция обслуживания: [VERCEL_DEPLOYMENT.md](VERCEL_DEPLOYMENT.md), результаты: [CLOUD_VERIFICATION.md](CLOUD_VERIFICATION.md).

## Локальный запуск

Нужен Node.js 24 LTS. На этом компьютере зависимости, .env.local и демонстрационная база уже подготовлены. Из папки проекта:

```powershell
.\scripts\dev.ps1
```

Или напрямую:

```powershell
$env:PATH = "$env:USERPROFILE\.local\node\node-v24.22.1-win-x64;$env:PATH"
npm.cmd run dev
```

Открыть http://localhost:3000/ru или http://localhost:3000/kk. Остановка — Ctrl+C. Для другого порта изменить BETTER_AUTH_URL в .env.local на точный origin и передать --port серверу.

На новом компьютере:

```bash
npm ci
npm run setup:demo
npm run dev
```

setup:demo создаёт случайный секрет, применяет миграции и заполняет отдельную SQLite-базу. Повторный запуск сохраняет изменения. Файл БД: .local/alatau-demo.sqlite. Пользователи, заявки, избранное, черновики и настройки переживают перезапуск Node.

## Вход и показ сценария

Вход: /ru/sign-in. Аккаунты: admin@alatau.demo, seller-a@alatau.demo, seller-b@alatau.demo, buyer-a@alatau.demo, buyer-b@alatau.demo. У каждого свой случайный пароль.

Посмотреть доступы локально: `npm.cmd run demo:accounts`. Команда выводит пароли только в ваш терминал; сервер не предоставляет их через HTTP. Локальная памятка .local/demo-credentials.json зашифрована AES-256-GCM, ключ выводится через HKDF из локального секрета окружения. После переноса доступов в менеджер паролей памятку можно удалить. Смена BETTER_AUTH_SECRET сделает старую памятку нечитаемой. В БД хранится только хэш пароля, которым управляет Better Auth. .env.local, .local, отчёты и трассы исключены из Git.

Для трёх ролей используйте разные профили браузера / приватные окна: обычные вкладки одного профиля разделяют сессию.

1. Покупатель: выбрать модель, добавить в подборку, указать количество/комплектацию, создать заявку.
2. Администратор: открыть её в /ru/admin, назначить продавца.
3. Продавец: открыть /ru/seller, уточнить состав, сохранить и подготовить расчёт.
4. Покупатель: обновить заявку, увидеть сумму, состав и публичную историю.
5. Продавец: завершить заявку. Это обработка, а не подтверждение оплаты/доставки.

## Реализовано

- Главная, каталог, категории, товар, поиск/фильтры/сортировка, адаптивность, RU/KK, контакты.
- Мастер `/door-finder`: тип, количество, бюджет за полотно, честные результаты и выбор существующего размера. «Моя подборка» остаётся на `/selection`.
- `/about` — информация о демонстрационном каталоге и процессе; `/projects` — «Идеи для интерьера» с AI-маркировкой. Содержимое отделено в `src/data/editorial.ts`.
- WhatsApp-предпросмотр в подборке: тот же состав и общая арифметика, копирование с ручным резервным способом. Чат не открывается, внешней отправки нет.
- Гостевые избранное и черновик локально; избранное и черновик покупателя в БД. Гостевой черновик можно явно импортировать после входа.
- Регистрация только BUYER; вход/выход, профиль, смена пароля, отзыв сессий при блокировке/смене роли.
- Покупатель: свои заявки, расчёты, история, отмена активной заявки.
- Продавец: назначенные заявки, комплектация, расчёт по прайсу, статусы, внутренние комментарии.
- Администратор: товары/варианты/цены/демонстрационное наличие, архивирование, аккаунты/роли/блокировка, назначения, контакты и тарифы услуг.
- Серверные проверки роли и принадлежности, строгие схемы, транзакции, revision для конфликтов, неизменяемые снимки расчёта. Покупатель не получает внутренние комментарии даже в API.

## Проверки

```bash
npm run typecheck
npm run lint
npm run build
npx playwright install chromium
npm run test:e2e
```

Playwright создаёт изолированную базу со случайными тестовыми аккаунтами, запускает production-сервер на 127.0.0.1:3100 и останавливает его. Порт должен быть свободен. Пользовательская демобаза не изменяется. Отчёт: npx playwright show-report; регрессионные снимки: test-results. Они содержат технические записи сценариев и не предназначены для презентации.

## Чистая презентация

```bash
npm run presentation:setup
npm run build
npm run presentation:start
```

Открыть http://127.0.0.1:3200/ru или http://127.0.0.1:3200/kk. Для разработки вместо start — `npm run presentation:dev`. Пароли только в локальном терминале: `npm run presentation:accounts`.

Набор `visual-v1`: 12 демонстрационных моделей, администратор, два продавца, два покупателя и пять заявок с осмысленными описаниями. Источник — `src/data/presentation.ts` и существующий seed товаров. Это отдельная `.local/presentation-demo.sqlite` со своим случайным секретом и зашифрованной памяткой доступов. Основная `.local/alatau-demo.sqlite` и `.env.local` не перезаписываются. Повторный setup сохраняет данные; обычный start/dev вообще не запускает seed. Для повторного показа неизменённого набора не редактируйте презентационные записи: автоматического сброса нет.

После сборки остановите презентационный сервер (Ctrl+C), затем выполните `npm run presentation:capture`. Команда сама занимает свободный порт 3200 и останавливает свой сервер по завершении. Она проверяет профиль/количество записей, только читает страницы, не создаёт тестовые товары и не выгружает пароли или браузерные сессии. Результат: [96 снимков и индекс](docs/screenshots/presentation/README.md), [манифест](docs/screenshots/presentation/manifest.json). Два языка × четыре размера × шесть страниц × viewport/full.

Production-сборка для локальной демонстрации:

```bash
npm run build
npm start
```

NODE_ENV=production — режим Next.js; APP_MODE=demo — демонстрационные данные. Это разные настройки.

## Размещение и ограничения

SQLite + Better Auth рассчитаны на один Node.js-сервер с постоянным диском. Нельзя размещать эту конфигурацию на эфемерном serverless-диске или запускать независимые реплики с разными БД. Для этого нужен PostgreSQL и адаптация серверного слоя. better-sqlite3 устанавливать на целевой ОС через npm ci, не переносить Windows node_modules на Linux.

Для реального запуска нужны отдельная чистая БД, новый секрет, APP_MODE=production, HTTPS BETTER_AUTH_URL, миграции (npm run db:migrate), резервные копии и проверка восстановления. Приложение отклоняет production-запуск с путём *demo.sqlite или БД с маркером seed; переименование демофайла не обходит проверку. Демо-seed в production запрещён. Безопасная выдача первого администратора на чистой production-БД требует отдельной процедуры внедрения; публичная регистрация его создать не может.

До коммерческого запуска остаются: подтверждённые ассортимент/контакты/фото/тарифы, политика персональных данных, проверка казахского текста носителем, резервное копирование, наблюдение за сервером, восстановление доступа и подтверждение email (писем в этой версии нет). В админке можно выбрать существующее изображение; загрузка новых файлов не реализована. Кабинет показывает последние 200 заявок; для больших объёмов нужна пагинация. Нет доставки, платежей, 1С, рассылок и сложного склада.

Четыре ранее отложенные функции реализованы: мастер, «О компании», интерьерные идеи вместо неподтверждённых работ и WhatsApp-предпросмотр. Принятый визуальный стиль сохранён. Реальные сведения о компании и выполненные проекты требуют подтверждённых материалов; отправка WhatsApp не подключена.

Пошаговый показ, получение доступов, описание изменяющих данные действий и безопасное архивирование презентационного набора: [DEMO_RUNBOOK.md](docs/DEMO_RUNBOOK.md). Снимки новых экранов: `npm run presentation:capture-completion`; прежние 96 PNG эта команда не перезаписывает.
